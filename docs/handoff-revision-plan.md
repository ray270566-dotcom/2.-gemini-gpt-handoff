# Gemini × GPT 交接工作流修订方案

提案日期为 2026-11-27，审查基线为 [`d499df2`](https://github.com/ray270566-dotcom/2.-gemini-gpt-handoff/tree/d499df285a7316810080049c81059fceed289827)。本文供审阅，所述流程待采纳和试跑。

## 修订目标

你向一个模型说明需求，另一个模型能在 Mac 或 Windows 上接手同一版本。你保留业务口径、范围取舍和上线决定。定位文件、整理共识、转述背景、核实提交和汇总测试结果由模型承担。

建议保留 Git 私库、Markdown 交接、严重问题优先和两轮后由你拍板的做法。日常选 Gemini 或 Codex 中更方便的一边作为主责入口。是否请另一方参与，取决于它能澄清哪项取舍、发现哪类错误，或缩短哪段等待。

## 一项任务该走多长的流程

| 遇到的情况 | 谁来做 | 交给你的结果 |
| --- | --- | --- |
| 目标明确，改动容易撤回 | 一个模型直接做并自测 | 改动、验证结果、仍有的限制 |
| 两条可行路线会明显影响成本、工期或使用方式 | 两边基于同一版需求、源码和样本独立拟案。都完成后，主责模型合稿 | 一份共识稿，只列需要你定的分歧、各自代价和推荐理由 |
| 涉及金额、数据写入、权限或对外消息 | 一个模型实现，另一方在独立会话中按业务口径核验同一版本 | 每条关键标准的预期、实测和差异 |
| 有三块以上可独立验收的工作，并行确实能省时间 | Gemini 按需启动 Swarm，给每块指定负责人、文件和验收条件 | 汇总后的结果和集成验证 |

同一任务可以既需要方案比较，也需要独立核验。只有一次简单改动时，直接用本次需求和自测结果即可。跨模型接手时才写交接单。

## 交接时，怎样确认对方接到了对的任务和版本

**一个任务有一个名字和一张交接单。串行接力时，同一时间只有一方写任务分支。** 建议把空白范本放在 `templates/`。实际发生交接时创建 `handoffs/<任务名>/task.md`，随任务分支一同推送。已有任务继续沿用原文件，等下次接手时再标明任务和版本。

| 交接单上写什么 | 接手者用它回答什么问题 |
| --- | --- |
| 任务名、原始目标、范围和验收标准 | 这次究竟要交付什么？怎样算做完？ |
| 状态、确认依据、当前负责人、下一步 | 我可以开始哪一步？还有哪项业务取舍待你决定？ |
| 已交付的实现提交、相关路径、运行方法 | 我要看哪份输入，从哪版代码继续？ |
| 已跑的检查、预期与实测、未解决的问题 | 我可以复用哪些证据？哪项还得重新核验？ |

状态从“草稿”进入“可执行”，前提是任务名匹配、验收标准可检查、影响本步的业务取舍已经有依据。若你的原始指令已给足授权，主责模型可引用该指令标记为可执行。模板、占位文字或上一个任务的确认均不能作为依据。独立规划阶段，两边可以读同一份事实材料，各自完成草案后再交换。实现完成后记为“待核验”，核验通过再记为“已完成”。

### 两台机器接力

1. **交出。** 串行接力默认共用 `task/<任务名>` 分支。发送方先提交代码和测试，再把这个实现提交号写入交接单，提交交接单并推送。推送成功后，给出一行接力消息，包含任务分支、交接单所在的提交链接及文件路径。用户在另一客户端粘贴这一行即可。
2. **接收。** 接手方先从远端获取更新，再切到接力消息指定的分支，将本地快进到该远端分支。核实消息中的交接提交和单内的实现提交均已包含在当前版本。工作区干净且版本相符，才开始下一步。普通 `git pull` 默认整合当前分支的上游，原方案中的两个模型分支因此可能各自显示最新，却拿着不同代码。[Git 官方说明](https://git-scm.com/docs/git-pull)
3. **出现差异。** 若分支已分叉、存在未提交修改或提交号对不上，保留现场，报告实际分支、当前提交和预期提交。并行工作确需独立分支时，先把选定成果集成到任务分支，后续核验以集成后的提交为准。
4. **交付。** 审查记录注明被测提交。审查之后若修改实现，重新运行受影响的检查并更新记录。如果只提交审查文档，保留原被测提交号即可。

例如，接手方已切到 `task/order-export-check` 后，可以运行 `git pull --ff-only origin task/order-export-check`。再用 `git merge-base --is-ancestor <交接提交号> HEAD` 检查版本包含关系。返回码 0 表示已包含。把占位符换为实际提交号，同样可检查实现提交。[Git 版本包含关系说明](https://git-scm.com/docs/git-merge-base)

## 第一项试跑与验收

用 HILO 订单导出检查做小规模试跑。以下金额和事件均为虚构样本，生产口径由你决定。约定按事件编号去重，订单数按不同订单号计算，同一订单的退款单独记一条负金额事件。

| 事件编号 | 订单 | 事件 | 金额 |
| --- | --- | --- | ---: |
| E01 | A | 收款 | 100.00 |
| E02 | B | 收款 | 60.00 |
| E02 | B | 同一条收款重复出现 | 60.00 |
| E03 | A | 部分退款 | -20.00 |

按上述约定，预期有 **2 笔订单、3 个唯一事件、净额 140.00**。核验方先从样本独立核数，再与导出结果比较。若重复计入 E02，净额会变成 200.00。若只漏掉退款 E03，净额会变成 160.00。验收时应能定位到具体事件及差额。作者的输出不能同时充当预期结果。

试跑同时检查四件事。

- 新会话只凭一行接力消息，就能找到正确任务、实现版本和下一步。
- 空模板或旧任务被交进来时，接手方能指出任务名或确认依据缺在哪里。
- 核验方能在候选结果中识别重复计入和遗漏退款，并给出对应差额。
- 记下你额外用于转述和核对的分钟数、人工中转次数、第二个模型独立发现的问题。与相近的单模型任务比较，再决定保留哪些步骤。
